# Schedule API load test with k6

Author: Maksim Kalinski. Branch: `test/k6-maksim`.

## Tool and purpose

k6 sends HTTP requests from virtual users and measures response time, request
rate and errors. I use it to check the cinema schedule when several visitors
request the same day's screenings. The existing Laravel routes and migrations
are used by the test stand.

This is my individual API-level assignment. The README reserves pgbench for
Jaromir's separate database-level work.

## Install and run

Start Docker Desktop in Linux-container mode. Run commands from the repository
root. The first command downloads the images and builds the PHP test image.
No host PHP or Composer installation is needed for this stand.

```bash
docker compose -f tests/load/compose.yml run --build --rm k6
```

This starts PostgreSQL, installs the locked PHP dependencies in a separate
Docker volume, runs the project's migrations, generates the large fixtures and
runs 10 virtual users for 30 seconds. The result is written to
`docs/testing/results/k6/latest.json`.

I also checked startup with a clean copy of the backend containing no `vendor`
directory or local `.env`. Dependency installation, migrations, fixture creation
and a short k6 run succeeded. Separate negative checks confirmed that k6 rejects
an empty-result fixture and that the SQL generator rejects another database.

To choose a short smoke test:

```bash
docker compose -f tests/load/compose.yml run --rm -e VUS=1 -e DURATION=5s -e RUN_ID=smoke k6
```

To repeat the whole measured comparison, use Node.js 24, which is also used by
our frontend. The suite builds the stand, tests the single-process server and
the multi-process setting, and saves six JSON summaries plus `suite.json` and
`environment.json`.

```bash
node tests/load/run-benchmarks.mjs
```

The default duration is 30 seconds per run. In Git Bash, this also allows a
shorter rehearsal:

```bash
DURATION=5s node tests/load/run-benchmarks.mjs
```

Rehearsals overwrite the named suite result files, so keep a copy of measured
results if needed. Exit code 99 from k6 means a threshold failed. The suite
records that result and continues the comparison. Other failures stop it.

## Local database and test data

The Compose project is `kino-load`, and the database is `kino_load`. Its database
port is internal to the Docker network. The PHP container has separate vendor,
cache and storage locations, and its local settings mask the host `.env` file.
The script's API target is fixed to `http://load-api:8000` inside this local
stand. Run it only on your own local Docker engine.

`tests/load/seed.sql` uses PostgreSQL `generate_series` to create repeatable data.
It rebuilds only the stand's fixture tables in one transaction, rejects any
database name other than `kino_load`, and runs `ANALYZE` afterwards. The schema
itself is created by the existing Laravel migrations.

| Table | Rows |
| --- | ---: |
| cinemas | 20 |
| halls | 100 |
| seats | 10,000 |
| movies | 100 |
| genres | 10 |
| movie_genres | 200 |
| users | 100 |
| screenings | 10,000 |
| bookings | 10,000 |
| tickets | 50,000 |

Each hall has 100 seats. Each screening has one booking and five valid tickets
for different seats in its own hall. All foreign keys and the existing unique,
price and non-overlap constraints remain enabled. Screenings are spread across
20 future days with five non-overlapping slots per hall per day. Emails use
`example.com`, and the records are synthetic.

`manifest.sql` records exact row counts, the next day's Tallinn time boundaries
and expected result totals in `fixture.json`. That runtime file is regenerated
before a test. It is also embedded in every saved measurement summary.

Jaromir can reuse this generator from his pgbench branch and credit this file.
To prepare only the data after the stand has been built:

```bash
docker compose -f tests/load/compose.yml run --rm load-seed
```

## Scenario and checks

The script requests `/api/screenings` with `per_page=30`. Virtual users alternate
between three queries using the fixture date:

| View | Filter | Expected total | Rows on first page |
| --- | --- | ---: | ---: |
| Day | date | 500 | 30 |
| Cinema | date and cinema_id=1 | 25 | 25 |
| Movie | date and movie_id=1 | 5 | 5 |

Each run has 15 sequential warm-up requests, followed by a constant number of
virtual users. Each virtual user sends one request, checks it and pauses for
0.2 seconds before continuing. Request timeout is 10 seconds. No browser,
poster downloads or frontend proxy are involved. Schedule response caching is
not implemented, and the stand uses the array cache store.

Every measured response must have HTTP 200, valid JSON, the expected total and
page size, and rows inside the selected Tallinn day. Cinema and movie queries
must also return the selected cinema or movie. A wrong or empty response cannot
count as a successful fast result. Setup stops immediately if the fixtures or
warm-up responses are incorrect.

The test records custom request counts, mean latency, p95 latency and the
fraction of responses that fail these checks. Warm-up requests are excluded
from these custom measurements. Reported RPS divides the measured request
count by elapsed run time after subtracting the timed setup, including the
final in-flight requests and pauses. Raw k6 metrics are retained in each JSON.

Thresholds require zero failed responses, all checks passing and p95 below
3,000 ms overall and for each view. The three-second value comes from the SRS
performance target. These large-data local measurements have different data
volumes from the SRS acceptance setup.

## Measured results

I ran the suite on 26 November 2026. Each row below is one 30-second run after
the warm-up. The API source and database schema were the same for all runs.
Only the worker setting and virtual-user count changed. The suite ran the
single-process configuration first, then the multi-process configuration.

Environment: Intel Core i5-12450H, 12 logical CPUs, about 15.7 GiB host RAM,
Windows 11, Docker Engine 29.7.2 with 12 CPUs and about 7.6 GiB RAM allocated.
The containers used PHP 8.4.25, Laravel 13.34.0, PostgreSQL 17.11 and k6 2.4.0.
The backend source was bind-mounted from Windows and dependencies were in a
Docker volume. Versions, source commit and image digests are recorded in
[environment.json](results/k6/environment.json).

| PHP worker setting | Virtual users | Measured requests | RPS | Mean ms | p95 ms | Errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Default single process | 1 | 84 | 2.78 | 156.50 | 294.66 | 0% |
| Default single process | 10 | 456 | 14.98 | 461.56 | 779.97 | 0% |
| Default single process | 30 | 480 | 15.09 | 1,726.81 | 2,383.31 | 0% |
| PHP_CLI_SERVER_WORKERS=4 | 1 | 89 | 2.95 | 135.74 | 241.51 | 0% |
| PHP_CLI_SERVER_WORKERS=4 | 10 | 999 | 33.13 | 98.91 | 181.82 | 0% |
| PHP_CLI_SERVER_WORKERS=4 | 30 | 2,483 | 81.71 | 163.41 | 289.35 | 0% |

In PHP's Linux development server, setting `PHP_CLI_SERVER_WORKERS=4` creates
four child workers in addition to the serving parent. The comparison therefore
uses one serving process versus five. The stand defaults to the latter setting;
setting `LOAD_WORKERS=1` makes `start-api.sh` unset the PHP worker variable for
the baseline.

All 4,591 measured requests passed both checks, giving 9,182 successful checks
and zero failed checks. All overall and per-view p95 thresholds passed. At 30
virtual users, the separate day/cinema/movie p95 values were 2,450.89 / 2,409.16 /
2,350.60 ms for the baseline and 291.09 / 291.44 / 287.48 ms for the multi-process
setting.

RPS means completed measured requests per second. Mean is average response
time. p95 means 95% of measured response times were at or below that value.
The errors column includes wrong schedule contents as well as failed HTTP
responses.

## Conclusion and limits

The default development server reached about 15 RPS at both 10 and 30 virtual
users. Adding users mainly increased waiting time, and p95 rose from about
0.78 seconds to 2.38 seconds. This suggests requests were queueing behind the
single PHP serving process.

With the multi-process setting at 30 users, throughput was about 5.4 times the
baseline and p95 fell by about 88%. This is a measured configuration improvement
using the same schedule queries and data. It shows that the serving setup is an
important limit in this local test. A production deployment should use a
proper web server and PHP-FPM with a measured worker configuration.

The schedule queries already have date and hall/date indexes. No indexes or
application query code were changed during the comparison. A useful next
experiment is caching frequently requested date/cinema schedule responses,
with invalidation when sessions change, and measuring again. That caching
improvement has not been measured here.

These are short synthetic tests on one computer, with the client and server
sharing resources. Each configuration has one measured run and there are no
confidence intervals. The order of runs, warm filesystem/database caches and
Windows bind-mount overhead can affect the comparison. The 0.2-second pause
creates an intentionally busy browsing pattern. The results apply to the tested
first-page schedule mix, with its existing indexes and artificial data.

The schedule reads screenings, movies, genres, halls and cinemas. The 50,000
tickets provide a consistent large fixture for future booking tests. Booking
contention, actual payment flows, production capacity and long-duration
stability require their own scenarios.
